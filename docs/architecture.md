# CloudflareSpeedTest 外部控制系统架构说明

## 1. 项目目标

本项目基于 CloudflareSpeedTest 的 Linux 二进制文件，构建一套运行于 Linux 内网环境的外部控制系统，核心目标包括：

1. 通过网页完整控制二进制程序
2. 支持参数与参数开关的可视化配置
3. 支持网页启动、停止、重启测速任务
4. 支持基于 systemd timer 的定时执行
5. 支持将优选 IP 推送到阿里云 DNS 与 Cloudflare DNS
6. 采用轻量文件存储，不引入数据库

---

## 2. 总体架构

系统建议拆分为四层：

### 2.1 Web 控制层

职责：
- 提供页面和 HTTP 接口
- 展示参数表单、运行状态、日志、结果、推送记录
- 接收用户操作并调用后端服务

建议技术：
- FastAPI
- Jinja2
- HTMX 或少量原生 JavaScript

### 2.2 任务编排层

职责：
- 创建执行任务
- 维护任务状态
- 控制启动、停止、重启
- 读取并生成 systemd timer 配置

核心要求：
- 页面操作不能阻塞请求线程
- 每次任务都要有唯一 ID
- 运行状态要可追踪

### 2.3 CloudflareSpeedTest 适配层

职责：
- 管理参数定义
- 根据网页配置构造命令参数
- 调用 CloudflareSpeedTest 二进制
- 采集 stdout/stderr
- 解析结果文件或结构化输出

这是整个系统最关键的适配层。上层永远不直接拼接 shell 字符串，而是通过参数定义模型生成最终命令。

### 2.4 文件与日志层

职责：
- 保存配置文件
- 保存任务运行元数据
- 保存优选结果
- 保存推送记录
- 保存日志文件

由于项目数据量很小，这一层直接基于 YAML / JSON / 日志文件即可满足需求。

---

## 3. 核心设计原则

### 3.1 网页必须是唯一控制入口

所有和 CloudflareSpeedTest 二进制运行有关的能力，都应通过网页完成，包括：
- 参数录入
- 参数开关
- 启动
- 停止
- 重启
- 定时任务配置
- 日志查看
- 结果查看

### 3.2 不做数据库优先设计

本项目只需持久化少量配置、日志路径、任务元数据与优选 IP 结果，因此不推荐引入数据库。优先采用文件存储，部署更轻，也更方便运维。

### 3.3 不做登录鉴权，但保留误操作防护

项目运行在内网，不做登录页和用户鉴权。但以下操作建议做二次确认：
- 停止任务
- 重启任务
- 覆盖 DNS 记录
- 删除模板或计划任务

### 3.4 定时任务交给 Linux 原生机制

应用只负责生成和维护定时配置，实际调度执行交给 systemd timer。这样做更符合 Linux 服务器的运维习惯，也更稳定。

## 5. 配置与数据组织方式

### 5.1 配置文件

建议放在 `data/configs/`：

- `binary_config.yaml`
- `dns_aliyun.yaml`
- `dns_cloudflare.yaml`
- `web_config.yaml`

### 5.2 参数定义

建议放在：
- `data/configs/parameter_definitions.yaml`

主要字段：
- 参数名称
- CLI flag
- 参数类型
- 默认值
- 是否显示
- 是否支持开关
- 参数分组
- 参数说明

### 5.3 模板文件

建议放在：
- `data/templates/*.yaml`

每份模板保存：
- 模板名称
- 每个参数的启用状态
- 每个参数的值
- 输出策略
- 推送策略

### 5.4 运行数据

建议放在：
- `data/runs/{task_id}.json`
- `data/results/{task_id}.json`
- `data/pushes/{push_id}.json`

## 6. 核心运行链路

### 6.1 手动执行链路

1. 用户打开网页参数控制页
2. 勾选参数开关并填写参数值
3. 系统根据参数定义生成命令预览
4. 用户点击启动
5. 后端创建任务 ID 并落盘任务元数据
6. 后端调用 CloudflareSpeedTest 二进制
7. 保存 stdout/stderr 到日志文件
8. 解析输出结果并写入结果文件
9. 页面展示运行状态、日志和优选 IP
10. 如配置自动推送，则进入 DNS 推送流程

### 6.2 停止链路

1. 用户在网页点击停止
2. 后端根据当前任务记录定位进程
3. 对目标进程执行受控终止
4. 更新任务状态为已取消或已停止
5. 页面刷新状态与日志

### 6.3 重启链路

1. 用户点击重启
2. 若当前任务仍在运行，先停止
3. 使用最近一次参数快照生成新任务
4. 分配新任务 ID
5. 启动新任务并更新页面状态

### 6.4 定时执行链路

1. 用户在网页创建计划任务
2. 系统生成模板引用和 systemd 配置
3. 写入 service 和 timer 文件模板
4. 启用或暂停对应 timer
5. 到达调度时间后，由 systemd 启动执行脚本
6. 执行脚本读取模板并运行测速

## 7. 模块边界

### 7.1 网页层不直接负责业务逻辑

页面只负责：
- 表单输入
- 状态展示
- 触发接口

具体任务控制、命令构建、结果解析、DNS 推送，都在服务层或适配层完成。

### 7.2 二进制适配层不感知网页

适配层只关心：
- 参数输入
- 命令构造
- 执行结果
- 错误处理

这样后续即使换成 CLI 管理入口或 API 调用，也能复用这一层。

### 7.3 DNS 推送模块与测速模块解耦

测速模块的职责是产出结果；推送模块的职责是消费结果并更新 DNS。二者通过结果文件衔接，便于独立调试。

## 8. 关键风险与应对

### 8.1 输出解析不稳定

风险：CloudflareSpeedTest 的控制台输出可能随版本变化。

建议：
- 优先依赖结构化输出文件
- 尽量不要用纯文本表格做唯一解析来源
- 为解析逻辑保留版本兼容层

### 8.2 停止任务不彻底

风险：网页点击停止后，子进程可能未完全退出。

建议：
- 记录 PID
- 采用分级终止策略
- 更新任务状态前先确认进程确已结束

### 8.3 无登录场景下误操作

风险：内网用户可直接操作页面。

建议：
- 限制来源网段
- 对危险操作增加确认弹窗
- 保留操作日志

### 8.4 systemd 文件与应用状态不一致

风险：网页显示和 systemd 实际状态不一致。

建议：
- 页面每次展示时都读取实际状态
- 不只依赖本地缓存配置

---

## 9. 推荐实施顺序

1. 先完成参数定义与命令构建
2. 再完成网页启动/停止/重启闭环
3. 再完成结果文件解析和页面展示
4. 再接入 systemd timer
5. 最后接入 DNS 推送

这个顺序能先把“网页控制二进制程序”这个最关键能力跑通，再逐步叠加调度和推送。

---

## 10. 最终建议

对你的场景来说，最佳方案不是做成一个重型平台，而是做成一个：

- Linux 内网运行
- Python 编写
- 文件型存储
- systemd 调度
- 网页完整控制
- DNS 推送可扩展

的轻量控制系统。

这会比引入数据库、鉴权系统、复杂前端或应用内调度器更贴近真实落地场景。
