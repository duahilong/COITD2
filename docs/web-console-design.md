# 网页控制台设计

## 1. 设计目标

网页控制台是整个系统的主入口，不是附属页面。它必须完整承载 CloudflareSpeedTest 二进制程序的控制能力。

首期必须实现：

- 参数配置可视化
- 参数启用/禁用开关
- 二进制路径和运行配置管理
- 任务启动、停止、重启
- 运行状态可视化
- 日志查看
- 结果查看
- DNS 推送控制
- 定时任务管理

由于项目运行在内网，首期不设计登录鉴权，但应通过页面交互降低误操作概率。

---

## 2. 控制台信息架构

建议控制台分为以下页面：

1. 仪表盘
2. 二进制配置页
3. 参数控制页
4. 运行控制页
5. 定时策略页
6. DNS 配置页
7. 日志页
8. 结果页

这八个页面已经足够覆盖你现在最关心的三件事：
- 几个模块的控制
- 日志显示
- 定时任务显示与控制

---

## 3. 页面设计说明

## 3.1 仪表盘

用途：
- 让用户在进入系统后快速了解当前状态
- 作为所有模块的总览页

展示内容：
- 当前是否有运行中任务
- 当前运行任务 ID
- 最近一次执行状态
- 最近一次优选 IP
- 最近一次 DNS 推送结果
- 最近几个任务列表
- 最近几个计划任务状态
- 最近日志异常摘要

建议操作：
- 快速跳转到参数页
- 快速启动最近模板
- 快速查看当前日志
- 快速查看最近一次优选结果

### 页面原型建议

顶部状态卡片：
- 当前运行状态
- 最近结果状态
- 最近 DNS 推送状态
- 当前启用的计划任务数量

中间区域：
- 最近任务列表
- 最近计划任务列表

底部区域：
- 最近错误摘要
- 最近优选 IP 摘要

## 3.2 二进制配置页

用途：
- 管理 CloudflareSpeedTest 二进制基础运行环境

字段建议：
- 二进制文件路径
- 工作目录
- 默认输出目录
- 默认超时时间
- 是否启用代理前检查
- 结果文件格式
- 日志目录

交互要求：
- 支持保存配置
- 支持校验路径格式
- 支持显示当前配置摘要

### 页面原型建议

左侧配置表单：
- 路径相关
- 输出相关
- 超时相关

右侧摘要卡片：
- 当前配置生效值
- 最后更新时间
- 最近一次校验结果

## 3.3 参数控制页

用途：
- 可视化维护 CloudflareSpeedTest 的执行参数

设计原则：
- 不展示原始命令行为主输入方式
- 以参数卡片或表单分组呈现
- 每个参数都具备独立开关
- 参数结构应直接映射统一 JSON 参数定义文件

建议分组：
- 基础参数
- 延迟测试参数
- 下载测速参数
- 输出参数
- 过滤参数
- 网络相关参数

每个参数建议字段：
- 名称
- 说明
- 启用开关
- 输入控件
- 默认值提示
- 校验提示

支持能力：
- 恢复默认值
- 保存为模板
- 从模板加载
- 复制当前配置为新模板

### 页面原型建议

页面分三栏：

1. 左侧：参数分组导航
2. 中间：参数表单区
3. 右侧：命令预览和模板操作区

中间每个参数卡片显示：
- 参数名
- 参数说明
- 开关
- 输入框
- 当前值来源
- 校验状态

右侧显示：
- 当前模板名
- 命令预览
- 保存模板按钮
- 重置按钮

## 3.4 运行控制页

用途：
- 对当前或最近一次任务做运行级控制

必须提供按钮：
- 启动
- 停止
- 重启
- 重新运行最近一次任务

必须展示：
- 当前状态
- 当前任务 ID
- 启动时间
- 已运行时长
- 使用的模板
- 本次参数快照
- 命令预览

交互要求：
- 运行中时，突出显示停止按钮
- 停止、重启需确认
- 若无运行中任务，停止按钮禁用

### 页面原型建议

页面上半部分：
- 当前任务状态卡片
- 操作按钮区

页面下半部分：
- 参数快照
- 运行日志摘要
- 结果跳转入口

如果当前无运行任务，则显示：
- 最近一次任务
- 最近一次执行结果
- 重新运行按钮

中间：

表格列建议：

## 4. 页面与统一 JSON 文件格式的关系

你提到希望各模块能够处理同一类文件，这一点对于网页端也非常重要。

因此网页端建议统一按以下方式读取数据：

- 参数页读取 `parameter_definition_set` 和 `parameter_template`
- 运行控制页读取 `task_run`
- 结果页读取 `task_result`
- 日志页读取 `task_log_index`
- DNS 页面读取 `dns_push_record`
- 定时页读取 `schedule_definition`

这样网页端几乎不需要为每个模块单独发明数据结构，整体维护会容易很多。

## 5. 关键交互规则

## 5.1 参数开关优先于参数值

即使某个参数有值，只要开关关闭，它就不应进入最终命令。

## 5.2 命令预览只做展示

命令预览是为了帮助用户理解系统即将执行什么，不应作为真实执行输入来源。真实命令必须由后端重新构造。

## 5.3 运行按钮与状态联动

- 运行中：显示停止
- 已结束：显示重新运行
- 停止中：按钮禁用
- 重启中：页面显示处理中状态

## 5.4 危险操作需要确认

建议确认的操作：
- 停止任务
- 重启任务
- 启用自动推送
- 覆盖 DNS 记录
- 删除定时计划

## 6. 页面数据流

### 启动任务

1. 前端提交参数表单
2. 后端校验参数
3. 后端生成命令预览和任务快照
4. 后端创建任务并启动进程
5. 前端轮询或局部刷新状态

### 停止任务

1. 前端发起停止请求
2. 后端定位 PID 并终止
3. 更新任务状态
4. 前端刷新状态和日志

### 重启任务

1. 前端点击重启
2. 后端读取最近参数快照
3. 后端停止旧任务
4. 创建新任务重新执行

### 查看日志

1. 前端选择任务或日志类别
2. 后端先读取结构化日志索引
3. 再按需读取原始日志文本
4. 页面分别展示摘要和明细

---

## 7. 页面实现建议

由于是内网项目，不必追求复杂前端框架。建议：

- 服务端渲染页面
- 局部区域使用 HTMX 刷新
- 只有少量动态行为使用原生 JavaScript

这样做的好处：
- 开发更快
- 部署更简单
- 后期维护成本低
- 与统一 JSON 文件结构更匹配

---

## 8. 可用性建议

1. 首页直接显示“当前是否运行中”
2. 参数页保留最近一次成功配置
3. 结果页突出显示最新优选 IP
4. DNS 推送结果要突出显示成功或失败
5. 错误日志与正常日志要有明显区分
6. 定时页突出显示异常计划任务
7. 日志页优先显示结构化错误摘要

---

## 9. 最终建议

网页控制台的重点不在于做得花哨，而在于把这些事情做稳：

- 参数不容易配错
- 运行状态看得清
- 日志查得到
- 结果拿得到
- 推送行为可控
- 定时任务能长期稳定运行

同时，网页端应尽量围绕统一 JSON 文件标准来组织页面数据。这样不仅能让几个模块共享一类文件格式，也能让后续代码实现更整齐、更容易维护。
