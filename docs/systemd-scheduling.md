# systemd 定时调度设计

## 1. 设计目标

本项目不采用应用内调度器，而采用 Linux 原生的 systemd service + systemd timer 实现定时执行。这样做的目标是：

- 提高定时任务稳定性
- 减少应用内部状态依赖
- 更符合 Linux 运维习惯
- 让计划任务具备更清晰的系统级状态与日志

---

## 2. 为什么选择 systemd timer

相对于应用内调度器，systemd timer 更适合本项目：

1. 调度不依赖 Web 进程常驻逻辑
2. 主机重启后恢复行为明确
3. 更方便与 systemctl、journalctl 等工具配合排障
4. 更适合内网 Linux 服务器长期运行
5. 可以把网页配置转化为系统级定时任务

---

## 3. 总体方案

网页负责：
- 创建定时任务配置
- 修改定时任务配置
- 展示计划状态
- 启用或暂停计划

systemd 负责：
- 到点触发执行
- 管理计划状态
- 输出系统日志

执行脚本负责：
- 读取模板配置
- 运行 CloudflareSpeedTest
- 生成结果文件
- 触发 DNS 推送

---

## 4. 推荐结构

建议增加以下目录：

```text
deploy/
  systemd/
    templates/
    generated/

data/
  schedules/
```

说明：
- `templates/`：放 service 和 timer 模板
- `generated/`：放根据网页配置生成的文件
- `data/schedules/`：放计划任务业务配置

---

## 5. 计划任务配置模型

建议每个计划任务保存一份 YAML 文件，包含：

- 计划名称
- 模板名称
- 描述
- 是否启用
- 执行方式
- timer 频率描述
- 结果推送策略
- 最近运行时间
- 最近结果摘要

这样网页端读取该文件即可展示计划任务列表。

---

## 6. service 设计建议

每个计划任务对应一个 service 文件。service 的职责是：

- 调用项目中的执行脚本
- 指定模板名称或任务标识
- 输出 systemd 级日志

建议 service 文件包含：
- Description
- WorkingDirectory
- ExecStart
- User
- Group
- Restart=no

不建议把复杂逻辑写入 service 文件，复杂逻辑应交由 Python 执行脚本处理。

---

## 7. timer 设计建议

timer 文件用于定义触发规则。

建议支持两类表达方式：

1. 固定周期
   - 每 5 分钟
   - 每 1 小时
   - 每天某个时间

2. 日历表达
   - OnCalendar 方式

网页上可以用更直观的配置形式，后台再统一转换为 timer 内容。

建议 timer 文件包含：
- Description
- OnCalendar 或 OnBootSec / OnUnitActiveSec
- Persistent=true
- Unit=对应 service

---

## 8. 网页与 systemd 的映射关系

网页页面不直接暴露 systemd 细节给普通使用者，而应做成业务化视图。

例如：
- 页面展示“每小时执行一次”
- 后端转换为具体 timer 表达
- 页面展示“已启用 / 已暂停 / 下次运行时间”
- 后端实际读取 systemd 状态

这能降低页面使用门槛，同时保留 systemd 的稳定性。

---

## 9. 建议的运行链路

### 创建计划

1. 用户在网页填写计划名称和模板
2. 选择执行频率
3. 后端生成计划配置文件
4. 后端生成 service / timer 文件内容
5. 保存到指定目录
6. 由部署脚本或管理流程启用 timer

### 修改计划

1. 用户修改计划
2. 后端更新计划配置
3. 重新生成 service / timer 文件
4. 刷新 systemd 状态

### 暂停计划

1. 用户点击暂停
2. 后端更新计划配置状态
3. 同步停用 timer
4. 页面刷新状态

### 启用计划

1. 用户点击启用
2. 后端同步启用 timer
3. 页面读取并刷新状态

---

## 10. 页面建议展示内容

在定时策略页建议展示：

- 计划名称
- 使用模板
- 执行频率
- 当前状态
- 下次执行时间
- 最近执行时间
- 最近执行结果
- 对应 service 名称
- 对应 timer 名称

---

## 11. 失败处理建议

### 11.1 计划执行失败

建议保留：
- 最近失败时间
- 失败摘要
- 对应任务 ID
- 日志跳转入口

### 11.2 systemd 配置与页面状态不一致

建议页面优先读取实际 systemd 状态，而不是仅依赖本地配置文件。

### 11.3 计划配置被手工修改

如果运维人员在服务器上手工改动了 service 或 timer 文件，网页应提供“状态不一致”提示。

---

## 12. 运维建议

1. Web 服务本身也建议由 systemd 托管
2. 计划任务执行账户应权限最小化
3. 日志目录需提前规划权限
4. 对 generated 文件目录做备份
5. 对计划配置文件做导出功能

---

## 13. 最终建议

在你的场景里，systemd timer 不是附加项，而是整套系统长期稳定运行的基础设施。网页负责让它“易配置”，systemd 负责让它“可靠运行”，这正是最适合 Linux 内网工具的方式。
