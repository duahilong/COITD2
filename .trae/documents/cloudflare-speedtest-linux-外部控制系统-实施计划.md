# CloudflareSpeedTest Linux 外部控制系统实施计划

## 1. 目标概述

基于 `CloudflareSpeedTest` 提供的 Linux 二进制文件，开发一套运行于 Linux 的外部控制系统，覆盖以下三部分能力：

1. 二进制文件控制
   - 启动、停止、重启
   - 参数模板与任务参数传递
   - 参数项开关控制
   - 定时执行
   - 运行状态与结果采集
2. IP 地址推送
   - 将测速产出的优选 IP 推送到 DNS 厂商
   - 首期接入阿里云 DNS 与 Cloudflare DNS
3. 网页控制部分
   - 通过网页完整控制前两部分
   - 在网页端管理参数、参数开关、运行、停止、重启、定时
   - 查看运行日志、历史结果、推送结果

本系统的核心原则需要明确为：

1. **凡是二进制程序控制相关的功能，都必须通过网页来完成。**
2. **项目运行于内网环境，首期不做登录鉴权。**
3. **定时任务优先使用 Linux 原生能力实现，推荐使用 systemd timer。**
4. **系统以轻量运行和易维护为目标，不引入数据库作为首选依赖。**

这意味着首期设计不能只提供“网页触发执行”，而要提供完整的网页控制台，覆盖：

- 二进制路径配置
- 参数录入
- 每个参数项的启用/关闭
- 参数模板保存与切换
- 启动任务
- 停止运行中任务
- 重启任务
- 定时任务开关与编辑
- 查看实时状态
- 查看任务日志和结果
- 查看推送记录

本阶段输出应包含：
- 对上游项目 CloudflareSpeedTest 的调研结论
- 技术选型建议，尤其是语言选择
- 一份完整的落地方案文档
- 后续实施的分阶段执行计划

## 2. 对上游项目的调研结论摘要

### 2.1 项目适合作为“外部测速引擎”而非内嵌库

CloudflareSpeedTest 更适合作为独立 CLI 二进制程序，由外部系统调度执行，再解析其输出结果，而不是尝试深度嵌入其内部实现。原因：

- 部署简单，适合 Linux 服务器
- 版本升级时对业务系统影响较小
- 适合通过参数驱动行为
- 适合通过输出文件或标准输出进行结果采集

### 2.2 集成方式建议

优先采用以下集成链路：

1. 外部控制系统生成本次任务参数
2. 调用 CloudflareSpeedTest 二进制文件
3. 采集 stdout/stderr 与结果文件
4. 解析出优选 IP 列表与关键指标
5. 通过 DNS 推送模块下发到厂商 DNS
6. 在网页端展示执行状态、日志与历史结果

### 2.3 运行注意点

- Linux 部署优先，Windows 不纳入主设计目标
- 必须将 CloudflareSpeedTest 视为“受控外部进程”
- 需要重点设计超时、并发控制、重试和日志归档
- 为了稳定集成，应尽量依赖结构化输出文件，而不是仅解析终端表格文本
- 若测速结果出现异常偏低延迟，需考虑代理干扰并纳入运行前检查

## 3. 技术选型建议

### 3.1 编程语言建议：Python 优先

结合你的倾向与该系统目标，推荐首选 Python。

### 选择 Python 的理由

1. 适合“外部进程控制 + Web 后台 + 文件存储 + API 集成”的组合场景
2. 对 Linux 友好，部署成熟
3. 对调用外部二进制、处理日志、解析 CSV/TXT、封装厂商 API 都非常高效
4. Web 生态成熟，后台管理页面开发效率高
5. 后续扩展更多 DNS 厂商成本低
6. 不依赖数据库也能快速组织出清晰的项目结构

### 3.2 不推荐作为首选的语言

- Go：性能和部署很强，但对“网页控制台 + 文件型配置管理 + 快速迭代”而言，开发效率不如 Python 灵活
- Node.js：做 Web 快，但进程控制、系统脚本和运维型任务的整体质感不如 Python 稳
- Java：过重，不适合这类轻量控制中台

### 3.3 Python 技术栈建议

建议采用：

- Web 框架：FastAPI
- 模板引擎：Jinja2
- 前端交互：HTMX 或少量原生 JavaScript
- 进程控制：subprocess / asyncio.subprocess
- DNS 厂商接入：requests / httpx
- 配置存储：YAML / JSON
- 结果存储：JSON / CSV / 文本文件
- 定时执行：systemd service + systemd timer

本项目首期更建议采用轻量服务器端渲染方案，不做前后端重型分离。

### 3.4 为什么 Python 特别适合“网页全量控制二进制程序”

因为你的要求不是只做一个 API 调度器，而是要做一个真正的“网页控制台”，让运维或管理员在网页上完成对二进制程序的全部操作。Python 在这方面有几个优势：

1. 很适合做“表单参数 -> 命令行参数”的转换层
2. 很适合做后台任务和进程状态管理
3. 很适合管理日志流转、运行记录和结果解析
4. 很适合快速搭建管理后台页面
5. 很适合把“参数开关”抽象成结构化配置，而不是写死命令字符串

因此，若目标是可维护的 Linux 管理后台，Python 是非常合适的选择。

## 4. 建议的系统架构

### 4.1 总体分层

建议系统拆为 4 个核心层：

1. Web 控制层

2. 任务编排层
   - 创建测速任务
   - 执行调度
   - 停止/重启任务逻辑
   - systemd 定时任务管理
3. CloudflareSpeedTest 适配层
   - 参数元数据定义
   - 参数拼装
   - 二进制调用
   - stdout/stderr 采集
   - 结果文件解析
4. 文件与日志层
   - 配置文件
   - 任务记录文件

   - 推送记录文件

### 4.3 针对“网页全量控制”的核心架构补充

为了满足你新增强调的需求，建议在 CloudflareSpeedTest 适配层中单独加入一层“参数定义模型”，不要让前端直接拼接命令行。推荐设计为：

1. 参数定义文件
   - 参数名称
   - CLI flag
   - 参数类型
   - 默认值
   - 是否支持开关启用
   - 是否必填
   - 是否在网页中展示
   - 参数分组

2. 参数实例文件
   - 某个任务模板下，该参数是否启用
   - 当前值是什么

3. 命令构建器
   - 根据网页中保存的参数配置，自动生成本次执行命令

这样可以保证：

- 网页上每个参数都可见
- 每个参数都可以单独开启/关闭
- 避免直接输入整段 shell 命令带来的风险
- 为后续扩展更多参数提供可持续能力

### 4.4 去数据库化架构说明

根据你的约束，这个项目不需要存储复杂业务数据，因此不建议首期引入数据库。推荐改为文件型存储：

1. `data/configs/`
   - 存放二进制配置、DNS 配置、参数模板
2. `data/runs/`
   - 存放任务运行元数据
3. `data/results/`
   - 存放每次任务优选出的一个或多个 IP
4. `data/pushes/`
   - 存放 DNS 推送记录
5. `logs/`
   - 存放 stdout、stderr、系统运行日志

这样做更符合你的场景：

- 数据量小
- 历史记录以排障和回看为主
- 部署更轻
- 迁移和备份更简单
- 更适合纯 Linux 内网项目

## 5. 功能设计方案

### 5.1 模块一：二进制文件控制

#### 核心能力

1. 二进制文件注册
   - 配置二进制路径
   - 校验文件是否存在、是否有执行权限
   - 记录版本信息

2. 参数模板管理
   - 支持保存常用参数模板
   - 支持按场景切换：延迟优选、下载测速、混合模式
   - 支持网页填写并转换为 CLI 参数
   - 支持参数启用/禁用开关
   - 支持参数分组展示

3. 任务执行控制
   - 手动启动
   - 停止运行中任务
   - 重启任务
   - 定时任务
   - 单次任务与周期任务区分
   - 页面一键复制最近一次配置重新执行

4. 运行状态管理
   - 待执行
   - 运行中
   - 成功
   - 失败
   - 超时
   - 已取消
   - 停止中
   - 重启中

5. 日志与结果采集
   - 保存标准输出
   - 保存标准错误输出
   - 保存结果文件
   - 提取关键指标（IP、延迟、速度、丢包率、地区码等）

#### 关键设计点

- 不能让网页请求线程直接长时间阻塞等待二进制执行完成
- 必须用后台任务机制执行
- 每个任务要有唯一 ID
- 必须设置最大运行时长与超时清理
- 应支持“参数快照”，保证历史记录可复现
- 停止任务要能定位对应进程，并执行受控终止
- 重启任务本质是“停止旧任务 + 按原参数重新创建新任务”

#### 网页必须提供的控制能力

这是本次需求修订后最关键的一部分。页面不能只是“提交一个任务”，而要成为完整的操作面板。

首期必须具备以下网页控制项：

1. 二进制基础配置
   - 二进制文件路径
   - 工作目录
   - 默认输出目录
   - 默认超时时间
   - 是否启用代理前检查

2. 参数管理界面
   - 以表单方式展示参数
   - 每个参数带启用/禁用开关
   - 支持布尔型、数值型、字符串型、路径型参数
   - 支持参数校验
   - 支持恢复默认值
   - 支持保存为模板

3. 运行控制界面
   - 启动
   - 停止
   - 重启
   - 重新运行最近任务
   - 查看当前运行状态

4. 任务编排界面
   - 立即执行
   - 延时执行
   - 周期执行
   - 启用/暂停某个定时任务

5. 运行过程可视化
   - 当前任务状态
   - 启动时间
   - 持续时间
   - 当前参数快照
   - 标准输出日志
   - 标准错误日志

#### 二进制参数的网页呈现方式建议

建议不要采用“命令行输入框”的形式，而应采用“参数卡片 + 开关 + 输入框”的形式。例如：

- 参数名称：下载测速数量
- 开关：启用 / 禁用
- 输入框：数值
- 说明：用于限制参与下载测速的候选节点数量

这样做的好处是：

- 运维人员不需要记命令
- 降低误操作概率
- 更容易做校验和审计
- 更适合后续保存模板和对比差异

### 5.2 模块二：IP 地址推送

#### 推送触发方式

支持三类触发：

1. 测速完成后自动推送
2. 测速完成后人工审核再推送
3. 从历史任务中选择结果重新推送

#### 结果选择策略

首期建议支持：

- 取 Top 1 IP
- 取 Top N IP
- 按阈值过滤（延迟、速度、丢包）
- IPv4 / IPv6 分开处理

#### 阿里云 DNS 接入

实现内容包括：

- AccessKey 配置
- 域名/子域名配置
- 记录类型配置（A / AAAA）
- TTL 配置
- 查询已有记录
- 覆盖更新或按策略更新

#### Cloudflare DNS 接入

实现内容包括：

- API Token 配置
- Zone ID 配置
- 记录类型配置（A / AAAA）
- Proxied 开关配置
- 查询记录并更新

#### 关键设计点

- 推送前要比较当前 DNS 记录与新结果，避免无意义更新
- 推送操作必须记录请求与响应摘要
- 失败时必须有可追踪日志
- 后续应预留回滚能力
- 网页上应能选择“自动推送”“人工确认后推送”“仅保存不推送”

#### 存储策略

推送模块也不需要数据库，推荐直接采用文件记录：

- 每次推送保存一份 JSON 结果
- 记录推送时间、目标厂商、目标域名、变更前记录、变更后记录、接口返回摘要
- 页面直接读取这些记录进行展示

### 5.3 模块三：网页控制部分

#### 设计目标修订

根据你的反馈，网页部分不是辅助功能，而是整个系统的主要控制入口。也就是说：

- 二进制程序的所有配置必须以网页可操作形式存在
- 参数及其开关必须网页可视化
- 运行、停止、重启必须由网页直接触发
- 定时任务也必须由网页创建和维护
- 不需要登录鉴权，但仍要注重内网环境下的误操作控制

因此，网页设计需要从“结果展示页”升级为“完整控制台”。

#### 首期页面建议

1. 仪表盘
   - 最近任务状态
   - 最近优选 IP
   - 最近推送结果
   - 当前运行中任务
2. 二进制配置页
   - 程序路径
   - 工作目录
   - 默认输出目录
   - 默认超时
   - 默认模板
3. 参数控制页
   - 参数列表
   - 参数分组
   - 各参数启用/禁用
   - 参数值编辑
   - 表单校验
   - 模板保存/加载/复制
4. 运行控制页
   - 立即启动
   - 停止当前任务
   - 重启最近任务
   - 重新运行指定历史任务
   - 查看当前命令预览
5. 定时策略页
   - systemd timer 配置说明
   - 启用/暂停计划
   - 指定所用参数模板
   - 查看下次运行时间
6. DNS 配置页
   - 阿里云配置
   - Cloudflare 配置
   - 目标域名记录配置
   - 推送策略配置
7. 日志查看页
   - 任务日志
   - 推送日志
   - 运行错误日志
8. 结果详情页
   - 单次测速结果列表
   - 可选择手动推送某条结果
   - 可复制为新任务配置

#### 网页端关键交互要求

1. 参数变更后，页面应实时生成“命令预览”
   - 仅用于展示本次将如何执行
   - 但后台真正执行时仍由服务端构建命令

2. 参数开关必须独立显示
   - 开启后才会进入最终命令
   - 关闭后即使有默认值也不参与执行

3. 运行/停止/重启按钮要和任务状态联动
   - 运行中显示“停止”
   - 已结束显示“重新运行”
   - 最近任务支持“重启”逻辑

4. 需要有历史参数对比能力
   - 能知道本次与上次任务参数差异

5. 即便没有登录鉴权，也建议保留操作确认
   - 比如停止、重启、推送 DNS 前做二次确认

#### 首期交互原则

- 先以后台管理系统为目标，不追求复杂前端交互
- 优先保证配置准确、执行稳定、日志可追踪
- 页面可读性优先于美观性
- 先把“控制完整性”做全，再做细节优化

## 6. 数据与文件模型建议

后续实施时建议至少设计以下文件对象，而不是数据库实体：

1. `binary_config.yaml`
   - 二进制路径
   - 工作目录
   - 默认输出目录
   - 默认参数
   - 运行超时

2. `parameter_definitions.yaml`
   - 参数名称
   - CLI flag
   - 参数类型
   - 默认值
   - 参数说明
   - 是否支持开关控制
   - 参数分组
   - 排序号

3. `templates/*.yaml`
   - 模板名称
   - 模板说明
   - 每个参数是否启用
   - 每个参数值

4. `runs/{task_id}.json`
   - 任务 ID
   - 执行参数快照
   - 状态
   - 开始/结束时间
   - 日志路径
   - 结果路径
   - 触发来源

5. `results/{task_id}.json`
   - 关联任务 ID
   - 优选出的一个或多个 IP
   - 每个 IP 的核心指标
   - 推送候选信息

6. `pushes/{push_id}.json`
   - 来源任务 ID
   - 目标厂商
   - 目标域名
   - 更新前记录
   - 更新后记录
   - 推送状态

7. `schedules/*.yaml`
   - 定时名称
   - 关联模板
   - timer 表达式
   - 是否启用
   - 最近运行时间

这样设计的优点是：

- 完全满足小数据量场景
- 便于人工查看和排障
- 便于备份与迁移
- 便于与 systemd 配置联动
- 后期如果真有需要，再迁移数据库也比较容易

## 7. 安全与运维设计

### 7.1 安全要求

- DNS 厂商密钥不能明文裸存，至少进行本地加密或权限隔离
- 虽然不做登录鉴权，但内网访问入口仍应限制来源地址
- 外部进程执行参数要做白名单校验，避免注入风险
- 禁止页面直接拼接任意 shell 命令
- 任务停止和重启应有二次确认，避免误操作
- 对 systemd 配置和二进制文件执行权限要做最小化控制

### 7.2 运维要求

- 推荐使用 systemd 托管 Web 服务
- 推荐使用 systemd timer 托管定时任务
- 日志建议文件归档
- 需要健康检查接口
- 需要异常任务自动清理
- 需要配置文件备份与导出能力
- 建议在 Linux 上将二进制执行账户与 Web 服务账户权限边界明确化

### 7.3 为什么推荐 systemd timer

与你的场景相比，systemd timer 比应用内调度器更合适：

1. 更符合 Linux 服务器运维习惯
2. 不依赖应用进程内部调度存活
3. 重启机器后恢复行为更可控
4. 更容易查看状态、日志和失败原因
5. 更适合将“网页配置”最终映射为系统级定时任务

因此，网页端应负责：

- 生成或更新定时任务配置
- 展示 timer 当前状态
- 提供启用/暂停入口

而真正的定时执行交给 Linux 原生机制完成。

## 11. 我对后续实施的推荐结论

### 推荐总方案

- 操作系统：Linux
- 核心语言：Python
- Web 框架：FastAPI
- 页面方案：Jinja2 + HTMX 优先
- 配置与结果存储：YAML + JSON + 日志文件
- 定时：systemd service + systemd timer
- 外部进程控制：subprocess
- DNS 接入：阿里云 DNS + Cloudflare DNS 抽象适配器
- 部署策略：内网部署、无登录鉴权、配合来源网络限制

### 推荐原因

这个组合最适合你的目标：
- 以 Linux 为主
- 以二进制控制为核心
- 需要完整网页控制台
- 需要调用外部服务 API
- 数据量很小，不值得为此引入数据库
- 更符合内网轻量运维工具的实际落地方式

### 后续第一步建议

一旦进入执行阶段，建议优先完成“阶段一：基础骨架与网页控制闭环”，先确保：

- CloudflareSpeedTest 能被受控调用
- 参数能从网页传入
- 每个参数都能在网页上开关控制
- 启动、停止、重启都能在网页执行
- 结果能被稳定解析
- 日志能被可靠保存
- 优选出的一个或多个 IP 能被以文件方式可靠保存

这是整个系统能否成功落地的关键基础。
